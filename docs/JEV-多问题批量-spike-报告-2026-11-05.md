## 6. 关键机制发现：`/v1/systemone` 在服务端按问题拆子任务（影响三项实验的共同前提）

### 6.1 产物内部可核实的证据（不依赖日志）

- **token 计费可加**：`equivalence.json` 中 180 个「样本×组」全部满足 `A.usage.input_tokens == Σ B 单问 usage.input_tokens`（0 例外，例如 s01/G1：A=292，B=201+91=292）。这说明打包请求的服务端用量是**各问题单问用量之和**。若服务端把整包作为一个 prompt 推理，则整包用量应显著小于各单问之和（共享 state 只算一次），而实测是精确相等。
- **答案逐字节相同**：A 与 B 的 answers 在 540/540 个问题上完全一致（`max|Δp|=0` 的原始来源）。
- **`usage.input_tokens` 随 N 近似线性增长**（H2 N=1/2/4/8/16/32 = 551/923/1807/3435/6831/13483），每增加一个问题约 +420 tokens，而不是“一次打包只多少量结构开销”。

### 6.2 只读服务端日志的旁证（本次 run 的观测，原始日志不入库；摘录见 `artifacts/jev-batch-spike/server-log-evidence.md`）

1. **任务数**：run 窗口（07:23–07:26 UTC）内 `slot launch_slot_/release` 共 **2740 个 slot 任务**；客户端共 **1458 个 HTTP 请求**，这些请求携带的问题总数按产物计算为 **2740 个**（H1-A 540 + H1-B 540 + H1-repeat 60 + H2-scan 652 + H2-A 480 + H2-B 400 + H3 覆盖 52 + H3 边界 12 + H3 探测 4，见附录 B 推导），**与任务数完全相等**。
2. **单任务 token 量**：窗口内任务 `n_tokens` 分布以 **333 / 372 / 443 / 551** 等小值为主（max 2744），全部 `truncated = 0`、0 条错误日志；从未出现等于 wire 规模（3435/6831/13483）的单任务。
3. **对照审计**（run 后额外 2 次请求，计入 §2）：
   - N=1（1 个 choice 问题）→ `usage.input_tokens=551`；日志出现 1 个 `n_tokens=551` 任务；
   - N=8（G2 形状 q1..q8 = 3×choice + 3×score + 2×noul）→ `usage.input_tokens=3435`；日志出现 8 个任务，`n_tokens` 恰为 `3×551 + 3×372 + 2×333 = 3435`（choice 551 / score 372 / noul 333，均 = 共享 state 前缀 + 1 个问题）；连同 N=1 的 1 个任务共 9 个任务，与日志 9 条 release 逐条吻合。
4. 日志中 `selected slot by LCP similarity, f_sim_best = 1.000` 表明各子任务复用同一 state 前缀的 KV 缓存。

### 6.3 结论与边界（推断性表述）

在该部署（llama.cpp `/v1/systemone` + d1-2B）中，**一次打包请求在服务端被拆成“每问一个子任务”逐题推理**，打包请求在本 run 的观测范围内未作为单个联合 prompt 执行。因此：

- 方案假设的“单请求 4096 token 上限”不是打包 wire 的约束；真实约束是**每个子任务的 prompt ≈ state + 1 个问题**。本次观测到的子任务 `n_tokens` 范围为 **333–2744**（H2 scan 的 411-state 任务 333–551；H3 边界/探针的大 state 子任务约 798–2744；H3 raw probe 10795/4≈2699/题），均低于 4096。
- `usage.input_tokens` 是**各子任务 prompt token 数之和**，不能当作“单个 prompt 长度”使用；H3 的 CALIBRATION=2.6386 主要反映逐题拆分的求和义务，而不是分词器对中文的系统性低估。
- H1 的 0 漂移与 H2 的“打包不省服务端计算”都由该机制解释。
- 该结论基于本次单 run、60 样本与 2740 条日志任务；若服务端/模型实现变化（真正的联合 prompt、换 tokenizer），三项实验必须重跑。

## 9. 执行偏差与计划外发现（必须与 §1 结论一起阅读）

1. **H2 N=32 只发 1 次探测**（偏离计划 Task 5“每个 N 扫 20 次”的 C1 安全修正，已获用户批准；另有 smoke 阶段 1 次 N=32 探测，本报告合计 2 次 N=32 探测）：预测 wire 5110 est tokens > 4096，为避免一次性额度被 2×5xx 熔断打挂，N=32 改为单次探测并标 `expected_over_context=true`、`skipped_repeats=19`、`pass=null`；实际结果 200 OK/616 ms，说明即便发满 20 次大概率也不会 5xx，但数据上 N=32 只有 1 个样本。H2-scan 实际 101 次（计划 120）。
2. **新增 transport 熔断**（I3，安全修正）：连续 3 次 transport 级错误（`status=None`）即 `SpikeAbort`，任何 HTTP 响应都会重置计数；本次 0 触发。
3. **画布 p95 口径**（I2）：用服务端 `duration_ms` 之和，剔除 20 ms 客户端节流；吞吐墙钟不变。`capacity.json` 记录 `sleep_seconds=0.02` 与 `canvas_latency_source`。
4. **无效比较判 conditional**（I4）：基础设施/解析噪声不再误判为“漂移”；本次 0 无效比较，未触发。
5. **边界子集口径**：样本文件 `boundary_tags` 是设计意图；本报告另给“事后由单问 B 答案选取”的经验子集（§表 C2），两者分别报告，经验子集不参看 A/B 翻转。
6. **样本长度覆盖**：long 层实际 510–774 字（≤801 est token），H1 未覆盖 1k+ token 的 state；2048 桶中除 `G2×N=8`（被公式拦截）外均由合成文本补齐（方案允许）。
7. **H3 边界证据有限**：正常 near/at/over 请求均被 `apply_window` 截断后发送（全部 200），H3 自身对“超 4096”的观察只有 1 个 raw probe（200）；H2 N=32 扫描探测与 smoke 探测（同样 est > 4096）也均为 200；`post_window_est > effective_context` 在 `enabled=true` 时数学上不可达，真实拦截只来自 `enabled=false`。

9. **服务端共享**：run 前后只读确认生产路由窗口内无业务请求；llama-d1 容器 `Unhealthy` 状态是既有状态（本次未重启、未改动）。

## 10. 建议

1. **不启动“单画布一次请求”的两段式改造**：H2 不通过（N≥4 的 p95 超 2× 单问、打包画布 p95 比串联高 7%–43%），收益只有 4.5%–9.5% 的问题吞吐。
2. **H1 结论可复用但不重标阈值**：0 翻转、0 路由差异；但该结论建立在“服务端逐题拆分 + 同 prompt”机制上，若服务端/模型形态变化（真正联合 prompt、换模型/换 tokenizer）必须重跑 H1。
3. **H3 需要重做预算模型**：不启用 `CALIBRATION=2.6386` 的窗口公式；正确口径应是“每问 prompt tokens（state + 单问）+ 问题数”双约束，并以服务端单任务实际 `n_tokens` 或 `usage.input_tokens / N` 标定。当前 wire 总 token 只影响 HTTP 体积，不构成 4096 限制。
4. 若仅想减少 HTTP 往返：最多把 N≤2 的同波画布打包，并接受 p95 上升；不要合并跨波（串联）问题。
