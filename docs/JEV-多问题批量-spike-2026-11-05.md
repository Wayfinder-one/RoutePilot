# JEV 多问题批量 · Spike 方案（“单画布一次请求”前置验证）

日期：2026-11-05
状态：**待执行**（本文只定义验证方案，不改生产代码）
关联现状：`router/routing/graph/engine.py` 按波次调用 JEV（`engine.py:212-224`），串联问题 = 多次请求；`tests/test_graph_engine.py:595` 固定了 `jev.calls == [["q1"], ["q2"]]`。
目标问题：把“一个画布内的全部问题合并成 **一次** `POST /v1/systemone`，拿到全部答案后再做逻辑判断”是否可行。

---

## 0. 一句话

在生产 d1-2B（llama.cpp）上验证三件事：**打包答案与最终路由是否等价于当前波次路径**、**单请求能塞多少问题且完整画布延迟可承受**、**prompt 预算公式是否可靠**。三项通过 → 可启动两段式改造；不通过 → 回退波次方案或先重标画布阈值。

---

## 1. 待验证假设

| 假设 | 内容 | 不成立的后果 |
|---|---|---|
| **H1 等价性** | 同一 `state` 下，打包与单问的答案误差可接受；全量答案按原图激活规则重放后，最终路由与当前波次路径一致 | “先问完再判断”会改变答案、最终路由或异常兜底，需重标阈值或保留波次 |
| **H2 容量** | 一次请求 N 个问题在 d1-2B 上无错误，问题吞吐和完整画布延迟不劣于当前串联基线到不可接受的程度 | 单次问题数必须设上限，大画布无法一次问完 |
| **H3 预算** | 校准后的 `estimate_tokens` 上界能覆盖完整 wire prompt，并提前识别超过 llama.cpp 单请求上限（生产约 4096 token）的请求 | 请求被 400/500，或 state 被过度截断 |

### 已有先验（不是结论，用于设计 spike 与判定线）

- 历史 d1-2B 参考（`--parallel 16`，**不是现行 8 并发基线**）：串行 p50 22.5ms / p95 26.5ms，约 78–80 rps（`smart-router-train/docs/llamacpp_d1_2b_deploy.md` §5）；本 spike 必须在现行配置上重新测量。
- 真实 2 问一次请求实测 **29.9–36.9ms**，`usage.input_tokens` 199–221（`case-logic.json`）；另有 1 问 **6 候选** `input_tokens` 384（`case-industry.json`）。两者问题形状不同，不能据此推算 state 复用或单问题 token 增量。
- 生产单请求上限约 **4096 token**（`-c 32768 --parallel 8 --ubatch-size 8192`），超限报 400/500；延迟随 token 增长：1460 tok≈89ms、2255≈103ms、3051≈143ms、3842≈199ms（同 §4.5）。
- 旧 0.8B 不同评分路径的漂移：`max|Δp|=0.0141`、`mean|Δp|=0.000326`、argmax 一致率 100%，但 0.5 阈值附近 2/480 翻转（`docs/JEV-P1-A-PII证据重算-2026-10-24.md:80-90`）。它不是 d1-2B 多问题打包的直接证据，只用于提示 H1 风险。
- 决策模型可能非确定（slot 调度/融合 kernel）：`llama.cpp` 社区提示“重复调用可能不同”，所以 H1 必须带**重复基线**（同请求跑两次）区分噪声与打包漂移。
- 代码引用的 trace 契约 spec §3.8/§3.9 与 `2026-11-02-canvas-first` spec 已不在仓库；本 spike 不依赖 trace 契约。

## 3. 样本与问题组

### 3.1 样本来源（60–80 条文本，脱敏后落盘、不入 git）

1. `docs/案例演示-2026-11-03/evidence/case-*.json` 的 `prompts[].text`：现有 5 棵案例树共 22 条记录、21 条唯一文本。
2. `configs/cases/*.json` 的节点 `instructions` / 选项 label+capability（用于构造问题组，不作为请求文本）。
3. 人工补足长度分层：短（<100 字）/ 中（100–500 字）/ 长（500–1500 字）各 15–20 条（以案例文案改写生成，避免引入真实敏感数据）。
4. 另设至少 20 条**边界子集**，可与长度分层重叠：noul 覆盖 `|p-t|≤0.05`，choice 覆盖 top-2 `margin≤0.05`，score 覆盖实际边条件 4/8 两侧。边界由单问基线预先选取，不得根据 A/B 翻转结果挑样；任一类没有边界样本时，对应 H1 结论只能为 conditional。
5. 保存为 `artifacts/jev-batch-spike/samples.jsonl`（该目录已由 `.gitignore` 排除），字段：`{"id","text","length_bucket","boundary_tags"}`。

### 3.2 问题组（模拟真实画布，wire 形状与生产一致）

构造必须与 `router/jev/client.py::_wire_question` 一致：`choice.criteria = {label: capability}`；`noul` 只有 `instructions`；`score.criteria` 为 2–10 个有限数值。

| 组 | 内容 | 用途 |
|---|---|---|
| G1 | choice(2 候选) + noul | 最小同波画布；当前引擎已合并成一次请求 |
| G2 | choice(4 候选) + score(5 档) + noul | 典型同波多问题画布；当前引擎已合并成一次请求 |
| G3 | choice(2 候选) → choice(2 候选) → noul → score(5 档) | 串联画布，当前为 **1–4 次请求**，H1/H2 重点 |

G3 必须同时保存为可执行图 fixture，固定节点、选项、边和 target，不能只保存问题数组。边条件固定为：`q1.prob.strong gt 0.65 → q2`、`q2.prob.strong gte 0.5 → q3`、`q3.yes gt 0.5 → q4`；`q4.value gt 4 → t-review`、`q4.value lte 4 → t-normal`，`error_fallback=t-error`。当前引擎统一使用 `error_fallback`，不得另写已不生效的 `otherwise_target`。因此前序条件不满足时，当前路径不会请求后续问题。

G1/G2 的 start 同时连接组内全部问题，用于测量同波打包；G3 用于测量串联波次。`state` 用生产模板渲染：`JevSettings.state_template.format(request=text)`（`router/jev/config.py:11`），不要另拼。

## 4. 测试 ①：等价性（H1）

### 4.1 做法

对每条样本 × 每组问题 G：

- 路径 A（打包）：1 次请求 `{"state": S, "questions": G 全部问题}`。
- 路径 B（单问）：N 次请求，每次只带 G 中 1 个问题，state 相同。
- 路径 C（当前波次基线）：仅对 G3，复用路径 B 的单问结果，在本地按 G3 fixture 做激活、三值逻辑和 target 选择，**不再发请求**。B 中未被激活问题的错误或无效答案不参与 C；已激活问题失败则按当前语义进入 `error_fallback`。
- 对 A 的全部答案使用同一套图实现做本地重放，比较 A/C 的最终 `target`、有序 `candidates`、激活问题集和 `error_fallback`。重放必须复用现有图条件、门和激活实现，不另写简化版逻辑。
- 第一版失败语义保守固定为：A 的传输/HTTP 失败，或任一请求答案缺失/非法，整次进入 `error_fallback`，不得静默忽略。记录相对 C 新增的兜底；若未来要容忍未激活问题失败，需另立设计和测试。
- 重复基线：抽 20 条样本，每组选 1 个关键单问，把路径 B 的该请求再跑一次，共 60 次，记录“同请求重复”的漂移。CLI 的 `--repeats 2` 只作用于该子集，不把完整 A/B 翻倍。
- 每条样本每组执行 1 轮完整 A/B，A/B 顺序交错；若同请求重复的漂移本身很大（> 0.01），先扩充基线再判断打包漂移，但不得突破总请求硬上限。

### 4.2 指标

| 范围 | 指标 |
|---|---|
| choice | 每个 label 的概率差 `Δp`（max/mean）、selected 是否一致、top-2 margin |
| noul | `Δp(yes)`、各实际阈值的判真是否一致 |
| score | `Δvalue`（映射后的档位值）、选中档位是否一致；使用 G3/案例的实际边条件 4/8，不套用概率阈值 |
| 条件判断 | 概率阈值 `0.5 / 0.6 / 0.65 / 0.7` 上的翻转；`gt/gte/lt/lte/eq/neq` 分开统计 |
| 端到端 G3 | 最终 target、candidates、激活问题集是否一致；A/C 请求数、新增 `error_fallback` 数 |

阈值翻转的最小统计单位是“样本 × 组 × 问题 × 算子 × 阈值”的一次判断。每组、每问题、每算子、每阈值分别报告 `翻转数/判断数` 和 95% Wilson 区间，不得只给全局混合比例；0 翻转时也要报告区间上界，不能表述为已证明真实翻转率为 0。

### 4.3 通过线（建议，可在执行前调整）

- argmax / selected 一致率 **100%**；
- `max|Δp| ≤ 0.02`，且同请求重复基线的 `max|Δp| ≤ 0.02`；基线超线时 H1 只能判 conditional。本 spike 不对单次重复测量做统计显著性检验；
- 各分层及边界子集的阈值翻转率均 ≤ **0.5%**（以旧 0.8B 实测 0.42% 为参考）；边界样本不足时不得判 pass；
- G3 最终 target 与 candidates 一致率 **100%**，A 相对 C 新增 `error_fallback` 为 **0**；
- 任一问题 `max|Δp| > 0.05` 视为异常，单独列清单人工复核。

超线处理：不直接放行，产出**阈值重标清单**（问题 id、算子、阈值、翻转方向、样本）和**路由差异清单**（A/C target、candidates、激活问题、兜底原因），作为后续画布校准依据。

### 4.4 输出

`artifacts/jev-batch-spike/equivalence.json` + 摘要表：

| 组 | 样本数 | 问题数 | max\|Δp\| | mean\|Δp\| | argmax 一致 | 分层阈值翻转 | 噪声基线 | 最终路由一致 |
|---|---|---|---|---|---|---|---|---|
| G1 | | | | | | | | 不适用 |
| G2 | | | | | | | | 不适用 |
| G3 | | | | | | | | |

## 5. 测试 ②：容量与延迟（H2）

### 5.1 单请求问题数扫描

- N ∈ {1, 2, 4, 8, 16, 32}：用 G2 的问题形状扩成 N 个**唯一 id** 的问题（q1..qN，候选数保持一致，避免混淆变量）。
- 固定中长 state（~300–500 token）；每个 N 串行 **20 次**。
- 指标：p50 / p95 / max 延迟、`usage.input_tokens`、HTTP 错误码与错误体、超时次数。

### 5.2 并发对比

- 场景 A（打包）：8 个并发画布 × 每画布 1 个 N 问请求，N=2/4，各 10 轮。
- 场景 B（当前串联基线）：8 个并发画布，每画布按 G3 fixture 逐波串行请求单问；只有前序答案满足边条件才请求下一问题，N=2/4，各 10 轮。
- B 的实际问题数可以小于 N；吞吐按实际完成问题数计算，请求预算仍按每画布最多 N 次计算。G1/G2 是同波画布，当前已经合并请求，不再用“N 个并行单问”冒充其基线。
- 主指标：**问题/秒**、**完整画布总延迟 p50/p95**、错误率；请求/秒只作辅助记录，不用于 70% 判定。
- 目的：同时确认打包是否减少完整画布延迟，以及“1 个大 batch”是否会长期占用 slot 而拖垮其他请求（`--parallel 8`）。

### 5.3 通过线

- N ≤ 8：错误率 0，p95 ≤ 2× 单问 p95；
- N > 8：**记录行为即可**（若 400/500/排队明显，给出“单次问题数上限”建议值）；
- 并发对比：场景 A 的问题/秒不低于场景 B 的 **70%**，且完整画布 p95 不高于 B；否则记录并建议“大画布分片或限流”，不得用请求/秒替代判定。

## 6. 测试 ③：prompt 预算标定（H3）

1. 固定并记录 wire JSON 序列化方式（`ensure_ascii=False`）。用 `router/jev/window.estimate_tokens` 估算**完整 questions mapping**（含问题 id、JSON 结构）和完整 state 模板；不得把逐 question 估算值相加后遗漏结构开销。
2. 常规样本优先复用 H1/H2 的请求与响应。对照 `usage.input_tokens`，覆盖估算 state 长度 256 / 1024 / **2048** token × N ∈ {1,2,4,8} × G1/G2；2048 用于覆盖既有生产配置。已有响应未覆盖的组合从 200 次预留额度补齐，不得额外突破总预算。
3. 计算 `est / actual` 分布与上界，确定保守补偿系数 `CALIBRATION ≥ 1` 和运行期安全余量 `SAFETY`（建议从 64–128 token 起，按实测偏差调），不得只按均值确定。
4. 边界验证：在预留请求额度内构造总 token 接近并超过 4096 的请求，记录错误码与文案，确认路由器侧必须拦截的条件。
5. 输出预算公式供后续实现使用。令 `raw_overhead = estimate_tokens(完整 questions JSON + 空 request 渲染的 state 模板)`，则：

```
effective_context = floor((jev_context_tokens − SAFETY) / CALIBRATION)
state_budget      = min(jev_input_tokens, effective_context − raw_overhead)
启用条件           = raw_overhead + MIN_INPUT_TOKENS ≤ effective_context
```

`state_budget` 是传给现有 `apply_window` 的原始估算预算。启用条件不满足时必须禁用打包，不得依赖 `apply_window` 把小于 `MIN_INPUT_TOKENS` 的预算自动抬升。最终公式必须使用同一 `CALIBRATION` 覆盖 state、questions 和模板，不能只对问题部分补偿。

通过线：校准后的预算上界在全部常规及边界样本上**不低估**实际；超限请求 100% 被公式提前识别。

## 8. 执行顺序与时间盒

1. 预检：确认 `.gitignore` 生效、当前 JEV 窗口和模型/服务配置；脚本只打印请求计划，预计超过 2000 次则停止。
2. smoke（10 分钟）：`/health` + `spike_systemone_graph.py` + 1 条样本 3 问。
3. 小批（20 分钟）：20 条样本 × G1/G2 跑 H1，复用响应做 H3；用单问基线确定边界子集。这 20 条计入全量样本，后续不得重复执行其 A/B。
4. 全量（≤2 小时）：含小批在内总计 60–80 条 × G1/G2/G3，复用已有响应，只补未执行的样本和组；每个 N 扫描 20 次，并发对比各 10 轮；H3 常规数据继续复用响应。
5. 出报告：结论表 + 阈值清单 + 路由差异清单 + 实际请求数 + 是否启动改造的建议。

## 9. 风险与注意事项

| 风险 | 缓解 |
|---|---|
| 给生产决策服务增加流量 | 错峰、默认可中断低并发，仅 H2 显式 8 并发；发送前预算检查，运行中硬上限 2000 次；不在业务高峰跑 |
| 决策模型非确定导致误判“打包漂移” | 必跑“同请求重复”基线；以基线为噪声上界，基线自身过大时只判 conditional |
| 样本含敏感文本 | 只用案例演示数据 + 改写合成；脱敏后落盘，产物目录由 `.gitignore` 排除，不写 DB、不入 git |
| `usage.input_tokens` 与服务端实际计费口径不一致 | 以服务端返回为准，同时在边界测试中抓 400 错误验证 |
| 大 batch 长期占 slot 影响在线路由 | H2 并发对比专门覆盖；发现明显退化 → 限制单次问题数 |
| 原本不激活的问题被打包后失败 | 保守进入 `error_fallback`，统计相对当前路径的新增兜底；不得静默忽略 |
